# PHASE 0 — CRITICAL BUGS (EPIC 0: Persistence & Auth Integrity)

**The three P0s are ONE underlying defect with three symptoms: the frontend has no durable owner identity.** Backend persistence + owner-scoping are correct and additive — the data is in SQLite. The breakage is entirely client-side: (a) the deployed build has Clerk compiled out (no build-time key), so durable identity never loads; (b) the create flow mints and overwrites a fresh per-browser capability token on every create. **Fix order: B2 (Clerk identity) → B3 (create reuses identity) → B1 resolves on its own → B4 (recover the orphaned "Longview TX" row, re-linked on first Clerk login per Owner Decision 2).**

### B2 — "CLERK_ENABLED=1 but never prompted to log in" *(fix FIRST — establishes durable identity)*
**Root cause (one line):** the deployed Vite bundle has Clerk **compiled out** because the Docker `web` build stage never receives `VITE_CLERK_PUBLISHABLE_KEY` (Vite statically inlines it at build time → `undefined`), so `<ClerkProvider>` never mounts and `clerkActive()` is `false`; separately, even when present, sign-in is an optional button, not a prompt/gate.

Evidence:
- `Dockerfile:34` `RUN npm run build` has **no `ARG`/`ENV VITE_CLERK_PUBLISHABLE_KEY`** before it (verified: lines around 34 declare no such ARG). Railway does not auto-inject service vars into a Dockerfile build unless the `ARG` is declared. Live bundle `assets/index-*.js` contains **0** occurrences of the key fragment / `pk_live_`.
- Chain: `web/src/RootProviders.tsx` `clerkPublishableKey()` → `undefined` → `<ClerkProvider>` never mounts. `web/src/auth/clerkToken.ts:22-24` `clerkActive() = Boolean(import.meta.env.VITE_CLERK_PUBLISHABLE_KEY) = false`. `web/src/components/TopBar.tsx` renders `<OwnerAuthControls>` only `{clerkActive() && …}` → never. `app/middleware.py build_csp()` emits the Clerk-widened CSP (backend Clerk genuinely ON), confirming the gap is frontend-only.

**Tasks:**
1. `Dockerfile` `web` stage: add `ARG VITE_CLERK_PUBLISHABLE_KEY` + `ENV VITE_CLERK_PUBLISHABLE_KEY=$VITE_CLERK_PUBLISHABLE_KEY` **before** `npm run build`; configure Railway to pass it as a build arg referencing the existing service var. Rebuild/redeploy.
2. **Verify:** the `pk_live_...` string now appears in the emitted bundle; the "Sign in" control renders; `/api/health` shows the new SHA.
3. Add a **forced sign-in prompt/gate** on owner surfaces (create/list/edit) — e.g. a `<SignedOut>` gate that drives `buildSignInUrl()` (or satellite auto-sync), while **preserving capability share-links for viewers (no login)**. Files: `web/src/auth/ClerkAuthProvider.tsx`, `web/src/auth/OwnerAuthControls.tsx`, route wrappers. *(Owner Decision 1 — RESOLVED: forced gate REQUIRED.)*
4. Confirm satellite FAPI CNAME (`clerk.thriftly.com`) + sign-in round-trip before declaring fixed. *(Owner Decision 3 — RESOLVED: shared-instance satellite config intended; round-trip must be live first.)*

**File scope:** `Dockerfile`, Railway build config, `web/src/RootProviders.tsx`, `web/src/auth/clerkToken.ts`, `web/src/auth/ClerkAuthProvider.tsx`, `web/src/auth/OwnerAuthControls.tsx`, `web/src/components/TopBar.tsx`.
**Golden / model_version impact:** none (auth/build only).

### B3 — "Only 1 projection saved; the second overwrote the first" *(fix SECOND — the real data-loss bug)*
**Root cause (one line):** the create POST sends **no `Authorization` header**, so every create is anonymous → the server mints a **fresh** `owner_token` each time and the client overwrites the single `localStorage` owner-token slot, **orphaning the prior projection** (its only access key is lost forever); the DB rows are NOT overwritten — both exist, but only the latest token can list.

Evidence:
- `web/src/pages/CreateProjectionPage.tsx:411-421` — the only create path POSTs with `headers: { "Content-Type": "application/json" }` (line 413) and **never calls `authHeader()`**; then `if (created.owner_token) setOwnerToken(created.owner_token)` (lines 419-420). Because the request is anonymous the server **always** returns a freshly-minted `owner_token`, so that guard is always true → the single slot is always overwritten.
- `app/routers/projections.py:687-746` — anonymous branch mints `secrets.token_urlsafe(32)` and returns it once; the `CapabilityBearer` reuse branch (`presented_owner = identity.token`, no new token) is never reached because the token is never sent.
- `app/store/sqlite.py:417-448` create is a pure additive `INSERT` (fresh `view_slug`, fresh `id`, no UPSERT) → two creates = two rows. List (`projections.py:749-789` → `sqlite.py:397-415`) is owner-scoped `WHERE owner_token_hash = ?`.

**Tasks:**
1. `CreateProjectionPage.onGenerate` must `await authHeader()` and attach `Authorization` on the POST → a 2nd+ create JOINS the existing owner workspace (server's `CapabilityBearer` reuse path already supports this). With Clerk signed in (B2), it sends the Clerk JWT and the server stamps `owner_clerk_user_id` (`projections.py:690-697`) → durable, additive, cross-browser ownership.
2. Stop blindly overwriting: only `setOwnerToken(created.owner_token)` when the server **actually minted** one (first-ever create) AND there is no existing identity.
3. **Test (Mutation Safety Quad addition):** two sequential creates from one browser → list returns BOTH. No server change required.

**File scope:** `web/src/pages/CreateProjectionPage.tsx`, `web/src/api/authHeader.ts`, `web/src/api/projections.ts` (`setOwnerToken`/`OWNER_TOKEN_KEY`). Server reuse path already correct.
**Golden / model_version impact:** none.

### B1 — "Saved locally not in DB / invisible in a private browser" *(resolves on its own)*
**Root cause (one line):** persistence is NOT broken — the row is durably written; the private window sees nothing because the owner list is scoped to a per-browser bearer token a private window does not have (`web/src/api/projections.ts:72-78` short-circuits to `[]` when `authHeader()` is empty), and B3 made it worse by rotating that token.

**Tasks:** do **not** "fix persistence" (it works). Once B2 (durable Clerk identity) + B3 (create reuses identity) land, the list keys on `owner_clerk_user_id` and the same signed-in owner sees all their projections from ANY browser, private or not.
**File scope:** none beyond B2 + B3. Add an e2e: sign in, create, open in a fresh/private session signed in as the same owner → projection visible.
**Golden / model_version impact:** none.
