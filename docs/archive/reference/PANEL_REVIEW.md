# Expert Panel Review — synthesis inputs

_Six expert lenses reviewing PRD v3.1, the engine, timpager patterns, gstack, and Superpowers. Captured during the build-doc synthesis._

## Product & Scope

**Summary:** This is a strategically sound, unusually well-disciplined PRD: it correctly reframes a calculator into a decision-and-funding tool with a sharp single-customer ICP (§2), an explainable rules-based recommendation (§12.3), and a trust/evidence layer (§15-16) that is the actual differentiator versus DIY spreadsheets and consultants. The milestone sequence is mostly right, and the M2 "smallest shippable loop" (§24/§28) is genuinely minimal and correct. The single largest scope risk is a hidden one: the PRD repeatedly calls the Python engine "the single math authority" (§13, §23, Appendix A), but the actual engine (generate_projection.py) implements the OLD model and does NOT compute the new product's core — it uses Year-2 midpoint instead of three explicit shares, has fixed-dollar supplies instead of % lines, has no Marketing line, no rent escalator, no monthly cash-flow, no break-even/capital-required/cash-gap decision metrics, no flags, and emits no view-model. Roughly 70% of what M1 needs does not exist yet, so M1 is an engine rewrite, not a "wire up." Second risk: M-1 pre-build validation (20 interviews, 10 manual projections, 5 board-shares, 3 paid/SQL conversions) is correctly gated but is the thing most likely to be skipped under build momentum, and the whole paid business model (§3) is still unconfirmed. The product is credible and defensible for v1 if the trust layer, the monthly cash-flow, and the decision recommendation ship together; without all three it is just another calculator.

**Key decisions:**
- TREAT M1 AS AN ENGINE REWRITE, NOT A REUSE. The build docs must state plainly that generate_projection.py is a starting skeleton, not the v1 authority. The new engine must add: three explicit shares (kill the Year-2 midpoint in compute() line 65 and methodology.md line 17-18); Marketing & outreach % (3.75%) and Supplies & processing as % of revenue (5.0%) replacing the fixed $3,700 supplies line; annual rent escalator (3.0%, Y2-Y3); $25k reserve buffer; the monthly M0-M12 cash-flow (§10) with donation S-curve ramp, hire-date payroll, timed startup outflows; and the decision metrics (break-even month, startup capital required = startup + |peak cash shortfall| + buffer, first-year cash gap, cash runway, sensitivity). These do not exist today.
- RESOLVE THE LABOR % DEFAULT BEFORE M1 (§7.3). The prototype shows 40%, the engine and methodology say 60%, Andy previously set 60%. This single number swings net margin and the go/no-go recommendation enormously (at ~$427k Y1 revenue the gap is ~$85k of payroll). Pick one product default, document the rationale (Longview actuals), keep the slider. This is a one-line decision that blocks every golden test.
- MAKE THE ENGINE EMIT THE VIEW-MODEL CONTRACT (Appendix D) AS ITS NATIVE OUTPUT. computed_json should serialize reco/metrics/kpis/monthly/rows/overrides/evidence/settings exactly as named so the React frontend and the .xlsx builder both consume one structure. This prevents a second math/format surface (the §13 anti-goal).
- LOCK M2 AS THE CREDIBILITY GATE, NOT M5. The smallest shippable loop must include the decision banner + monthly cash-flow + recommendation, because those ARE the product. The current M2 wording (§28) says 'minimal inputs -> compute -> save -> reopen -> .xlsx + basic packet' but is silent on whether the decision outputs are in M2. Decision: capital-required, break-even month, and the rules-based recommendation (§12.3) MUST be in M2; research, overrides, narrative, and evidence attachments stay deferred. A calculator without the decision is not shippable for this ICP.
- SHIP THE THREE SAMPLE PROJECTIONS AS GOLDEN FIXTURES FROM DAY ONE. House of Hope conservative (6/8/10%, ~$427k Y1, ~11% margin, ~$278k capital, break-even ~month 5-7), the Aggressive flagged case (15/20/25%, ~39% margin, must trigger the §12.2 guardrail + required justification), and the Grace Mission loss case (Y1 net ($12,400), payback N/A, $14/sqft low-confidence rent, one overridden Payroll cell). These drive design, the §12.4 edge-case math, and the golden/LibreOffice reconciliation tests (§13/§18).
- KEEP TRADE-AREA SCOPE LOCKED TO CITY/COUNTY/MANUAL (§8). Radius/ZCTA stays deferred with its rules pre-specified. Do not let this expand in v1 - it is the most tempting and least ICP-critical scope creep.
- DO NOT BUILD ACTUALS/BENCHMARKS (§6.3, M7) OR DATA-COMPOUNDING IN V1 BEYOND THE EMPTY TABLE. It is correctly post-launch; the moat is real but premature. Ship the actuals table schema (§24) so it is not a migration later, but build no UI.

**Must-haves:**
- Monthly launch cash-flow (§10) with break-even month, minimum-cash trough, and cumulative cash - this is the new core that distinguishes a decision tool from a 3-year P&L and surfaces early-failure risk.
- Rules-based, explainable recommendation (§12.3) with the reasons shown - proceed / revise / find cheaper rent / raise more cash / delay / do not proceed. The recommendation IS the job-to-be-done (§4).
- Startup capital required and first-year cash gap (§12.1) prominently on the decision banner with a 'Why?' drill-down - this is the number a board votes on.
- Three explicit per-year donor shares (§7.1) with the live plain-language helper ('X% of ~N households -> ~D donations/week -> ~$R revenue') and benchmark presets - non-finance users cannot reason about market share without it.
- Forecast guardrails (§12.2) that flag out-of-band inputs AND require a justification note that travels into the packet - this is what makes the output defensible to a skeptical board/funder.
- Evidence/confidence on every researched number (§15) with verified-vs-estimated visual separation - trust is the differentiator vs. a spreadsheet.
- Server-authoritative compute as the only math surface (§13) with version-locking (no silent recompute) and the golden + LibreOffice reconciliation gate (§18) - correctness is the entire value proposition for a finance tool.
- Edge-case math discipline (§12.4): explicit null + flags map, N/A handling, parentheses for negatives, never #DIV/0! in Excel - the Grace Mission loss case must render cleanly.
- Autosave / no-login capability-token model (§19.3, §20) with the save-conflict 409 path - the designed interaction loop depends on it.
- Terms-acceptance gate before export/share and AI opt-out path that still computes + exports .xlsx (§21) - legal defensibility and the 'planning estimates, not advice' disclaimer.

**Risks:**
- ENGINE-REUSE FICTION: The PRD's central claim that the Python engine is 'the single math authority' is not true today - the engine computes the old model and ~70% of v1 math (monthly cash-flow, decision metrics, % cost lines, escalator, three shares) is unbuilt. If the team reads 'reuse the engine' as 'it's mostly done,' M1 will be badly under-estimated. Mitigation: build docs must scope M1 as a rewrite with a line-by-line gap list.
- M-1 VALIDATION SKIPPED: The pre-build gate (20 interviews / 10 manual projections / 5 board-shares / 3 paid-or-SQL conversions) is the highest-leverage and most-skippable step. Building M0-M7 before confirming anyone will pay (§3 price/gate is explicitly unconfirmed) risks a beautiful tool no board buys. Mitigation: make M-1 a hard gate with named exit criteria in the build process.
- LABOR % UNRESOLVED (§7.3): 40% vs 60% is an open product decision that materially flips the recommendation between Proceed and Raise-more-cash on the same inputs. Shipping with the wrong default undermines credibility on the very first projection a board sees.
- DECISION-METRIC CALIBRATION: break-even, ramp S-curve (§10.2), and capital-required depend on assumptions (ramp length, seasonality, peak shortfall) that have never been calibrated against a real opening. A confidently-wrong break-even month is worse than none. Mitigation: label confidence, show sensitivity, and treat §6.3 actuals as the calibration backlog.
- SCOPE CREEP INTO RESEARCH/RADIUS/ACTUALS: Three tempting expansions (drive-time trade areas, demand drivers actually scaling the estimate, actuals benchmarking) are all explicitly deferred but all individually seductive; any one pulls v1 past credible.
- GROUNDED-NARRATIVE OVER-PROMISE (§17): the numeric-grounding validator (every prose figure must exist in computed_json) is non-trivial; if it leaks an unverified number into a board packet, trust is destroyed. This is M5 and rightly late - risk is pulling it forward.
- TWO-TAB AUTOSAVE + OVERRIDE DAG COMPLEXITY: cell-level overrides on a topological DAG with an inspector (§14) is the most complex UX in the app and is correctly deferred to M4; pulling it into MVP would sink M2.

**Doc notes:** Build markdown should include: (1) An ENGINE GAP TABLE comparing generate_projection.py as-built (DEFAULTS lines 32-53, compute() lines 63-94, Year-2 midpoint line 65, fixed supplies line 45) against PRD §7.3/§10/§12 requirements, marking each row EXISTS / REWRITE / NEW - so M1 is correctly scoped as a rewrite. (2) A MILESTONE CREDIBILITY MAP marking which milestone first makes the product defensible to a board: M2 must carry the decision banner + monthly cash-flow + recommendation (not just compute+save+xlsx as currently worded in §28). (3) A SAMPLE-DATA FIXTURE SPEC with the three named projections (House of Hope conservative 6/8/10%; Aggressive flagged 15/20/25% triggering §12.2; Grace Mission loss case with negative Y1, N/A payback, low-confidence $14/sqft rent, one overridden Payroll cell) including expected outputs (Y1 ~$427k, ~11% margin, ~$278k capital, break-even ~month 5-7 per Appendix D) as golden-test targets. (4) A RESOLVED-DEFAULTS table that closes §7.3 open items (pick labor %; confirm marketing 3.75%, supplies 5%, escalator 3%, reserve $25k, basket $17.08, donations/hh 3). (5) The VIEW-MODEL CONTRACT (Appendix D field names) as the engine's native output schema, shared by frontend and .xlsx builder. (6) GOALS/NON-GOALS restated: in = decision+funding tool for first-store nonprofits with city/county/manual trade area; out (v1) = multi-store, for-profit, radius/ZCTA, actuals/benchmarks, demand-drivers-scaling-estimate. (7) An OPEN-QUESTIONS-TO-CLOSE list elevating §29 items that block the build: business-model price/gate, labor default, ramp/seasonality calibration source.

## Backend & Architecture

**Summary:** The PRD is architecturally sound and the FastAPI + SQLite(WAL)+Litestream + capability-token shape is the right call for a no-login, single-host, low-write product. The central risk is the "reuse generate_projection.py as the single math authority" claim: the existing engine is NOT reusable as-is. Its compute() is annual-only (3 years), hard-codes Year-2 = midpoint of Y1/Y3 (PRD §7.1 explicitly forbids auto-midpoint and requires three explicit shares), has no monthly cash-flow, no marketing line, treats supplies as a fixed dollar amount (PRD §7.3 wants % of revenue), has no rent escalator, no decision metrics, no overrides/DAG, and returns positional tuples instead of the §App-D view-model. So §13's "reuse" must be reframed as "extract and extend the formulas into a pure compute core, with the .xlsx/.docx builders rebuilt to the §18 cell contract." The math in generate_projection.py is the seed of truth, not the finished authority. Everything else — version-locking computed_json, optimistic concurrency via If-Match/version, data-access interface with a Postgres path, the endpoint surface — is well-specified and maps cleanly to modules. The golden-test gate (§13/§18) is the keystone that makes the single-authority claim enforceable and must be built in M1 before any UI depth.

**Key decisions:**
- Reframe 'reuse the engine' (§13, §23): split generate_projection.py into (a) a PURE compute core `engine/compute.py` with zero openpyxl/docx imports that takes a normalized inputs+assumptions+overrides dict and returns the §App-D view-model (reco, metrics, kpis[], monthly[], rows[], overrides[], settings, computed_json+flags), and (b) renderers `engine/xlsx.py` and `engine/packet.py` that consume the compute output. The current file mixes math and Excel-cell construction in build_xlsx()/build_docx() and cannot serve a web API. Keep the formula constants (DEFAULTS dict, EXP_LINES) as the literal seed but they must be EXTENDED, not copied: add marketing %, supplies-as-% , rent escalator, three explicit shares.
- Make the compute core a stateless, deterministic, side-effect-free function: `compute(inputs, assumptions, demand_drivers, trade_area, overrides) -> ComputeResult`. Pin `model_version` (semantic, e.g. '2.0.0') and a separate `compute_schema_version` (shape of computed_json) as module constants. computed_json is persisted WITH model_version; on read, if stored model_version != current, return the stored snapshot verbatim and surface an 'upgrade available' flag — never recompute silently (§13). upgrade-model writes a NEW revision so the prior is preserved.
- Implement the override DAG (§14) inside the compute core as an explicit topological evaluation: nodes are keyed `"{node}#{year}"` matching overrides_json (§24). Pinned nodes short-circuit to their value; derived rows/KPIs are non-pinnable (reject at the API boundary, not just the UI); detect and flag upstream rows that no longer drive any pinned downstream (the 'no back-solve' rule). The monthly model and the 3-year roll-up must both flow through this single evaluator so annual totals derive from the monthly months (§10.2/§10.3) and never disagree.
- Data-access layer (§22, §26): define a `Store` Protocol/ABC (Python typing.Protocol) with explicit methods — get_projection_by_slug, get_by_owner_token, create, update_with_version_check (returns rows-affected for 409), insert_revision, list_evidence, etc. Ship `SqliteStore` for v1 and write the interface so `PostgresStore` is a drop-in. CRITICAL: do NOT leak SQLite-isms (e.g., last_insert_rowid, INSERT OR REPLACE) above the interface; use UUID/ULID string PKs generated in app code (matches timpager's TEXT PRIMARY KEY UUID convention) so the Postgres path needs no ID-strategy change.
- Optimistic concurrency (§24/§25): `version` is a monotonically incrementing INTEGER per projection. Every mutating endpoint requires `If-Match: <version>`; the UPDATE is `... SET version=version+1, ... WHERE id=? AND version=?` and a 0-row result returns HTTP 409 with the current server state in the body so the UI can offer reload/overwrite/save-as-copy (§19.4). Return the new version in an `ETag`-style response header and in the body. Autosave (§19.3) means high write frequency on a single row — debounce on the client, serialize writes server-side (single writer, WAL), and each settle writes one revision snapshot.
- Token handling (§20/§24): store owner_token_hash and edit_token_hash (SHA-256), compare constant-time; view_slug stored plaintext as the lookup key. Tokens are >=256-bit (owner) / >=128-bit (view_slug) generated with secrets.token_urlsafe. Edit/recovery secrets arrive via URL fragment and are sent as `Authorization: Bearer`; never accept secrets in path/query, never log Authorization headers or fragments. rotate-tokens regenerates and re-hashes, invalidating shared links (§20).
- LLM + research as bounded async services, never in the compute hot path (§16/§17): `research/` fetches sources server-side, stores them, and the LLM call is extract-only over provided snippets with post-hoc citation validation (reject unfetched citations). `narrative/` generates from computed_json facts with post-generation numeric grounding (every figure must exist in computed_json) and stores computed_hash for stale detection. Both use Anthropic-primary/OpenAI-fallback behind a thin provider router (mirror timpager's lib/ai-router.js pattern). Compute (<50ms, §27) must work fully with these disabled (§21 opt-out).
- Boot-time config validation mirroring timpager SECURITY.md: refuse to boot in production if required secrets/env unset (ANTHROPIC_API_KEY needs a fallback-allowed companion, CENSUS_API_KEY, GOOGLE_PLACES_API_KEY, DB_PATH, GITHUB_TOKEN/REPO, CRM_API_KEY). Make DB_BACKEND explicit ('sqlite'|'postgres') so the data-access path is never ambiguous — directly reuse timpager's DB_BACKEND + DB_PATH/DATABASE_URL pattern.

**Must-haves:**
- A pure, deterministic compute core decoupled from openpyxl/python-docx, emitting the §App-D view-model AND the persisted computed_json+flags. No web request may import the Excel/Word builders to get numbers.
- Golden-test harness in M1 (§13/§18) BEFORE override/UI depth: assert server compute == reference-engine values AND == LibreOffice recalc of the exported .xlsx (tolerance < $0.50 / 0.1pp, zero formula errors), with AND without overrides. recalc.py is directly reusable for the LibreOffice half; wire it into CI as blocking.
- model_version + compute_schema_version constants persisted on every computed_json; read path never silently recomputes on a newer engine (§13). upgrade-model creates a new revision, preserving the prior.
- If-Match/version optimistic concurrency on all mutations with a real 409 + current-state body (§24/§25); single-writer WAL + busy_timeout; one revision snapshot per autosave settle (§19.3/§24).
- Data-access Store interface (Protocol) with SqliteStore now and a documented PostgresStore path; app-generated string PKs; no SQLite-specific SQL above the interface (§22/§26).
- Constant-time hashed-token auth, owner-scoped list (never global), secrets only via Authorization header / URL fragment, no secrets in logs or paths (§20).
- Override DAG evaluator with non-pinnable derived rows enforced server-side, topological recompute, and stale-upstream flagging (§14) — shared by both the monthly and annual paths.
- Monthly-first model where Year-1 annual totals are a roll-up of M0-M12 so the two never disagree (§10.2/§10.3); decision metrics (capital required, cash gap, runway, break-even month, recommendation) computed in the core (§12).
- Engine extensions the current file lacks: three explicit shares (drop Y2=midpoint), marketing % line, supplies as % of revenue, annual rent escalator (Y2-Y3), reserve buffer into capital-required (§7.3/§12.1).
- Litestream continuous replication to object storage on the /data volume with a documented restore drill, RPO/RTO, and backup purge limits (§21/§26) — reuse timpager's litestream.yml + railway.toml shape (volume mount, healthcheckPath, numReplicas=1, restartPolicy).

**Risks:**
- OVERSTATED REUSE: §13/§23 imply generate_projection.py is the ready-made authority. It is not — it is annual-only, midpoint-Y2, fixed-dollar-supplies, no monthly/marketing/escalator/overrides, and returns tuples. If a builder takes 'reuse' literally they will wrap the Excel builder behind an API and inherit a model that contradicts §7.1/§7.3/§10. The build doc must say 'extract & extend the formulas, rebuild the renderers,' not 'wrap.'
- Two compute surfaces drift: the Python compute core and the .xlsx live formulas are independent implementations of the same math. Without the golden gate they WILL diverge as the model grows (marketing, escalator, monthly). The §18 gate is the only thing keeping the single-authority claim true; if it slips out of M1 the whole trust story is hollow.
- Autosave write-amplification on SQLite single-writer: debounced autosave (§19.3) + a revision snapshot per settle can produce heavy writes on one row plus an append-only revisions table; under Litestream this is fine but unbounded revisions need a retention/compaction policy, and concurrent edit links (§20) on one projection can serialize-stall. Quantify expected write rate and cap revision growth.
- <50ms compute budget (§27) is plausible for the annual model but the monthly model (M0-M12 x line items x DAG topo-sort) plus override resolution per keystroke (debounced) is heavier; needs a perf test in M1, and the budget should be stated as p95 server compute excluding research/LLM.
- Postgres path is asserted (§22/§26) but SQLite-specific habits (INSERT OR REPLACE, rowid, WAL-only assumptions, pragma busy_timeout, JSON1 functions) can quietly leak into queries and break portability; without a conformance test running the same suite against both backends, the 'drop-in' claim is aspirational.
- computed_schema_version vs model_version conflation: the PRD names model_version but the §App-D view-model can evolve independently of the math. If only one version is tracked, a renderer/shape change can be mistaken for a math change (or vice-versa), corrupting stale-detection and upgrade prompts. Track both.
- LLM grounding enforcement is a backend invariant, not a prompt nicety: the numeric-grounding check (§17) and citation-rejection (§16) must be hard server-side validators that fail the response, or unverified figures reach the board packet. Easy to under-implement as 'we asked the model nicely.'
- Capability-token model + autosave + no login means a leaked edit fragment is full write access with no second factor; rotate/revoke (§20) must be implemented in v1, not deferred, and the revision log must record actor_token_hash + access events for forensics.

**Doc notes:** Write a BUILD_ARCHITECTURE.md that contains: (1) Project layout — `app/` (FastAPI): `app/main.py` (boot + config validation), `app/deps.py` (auth dependency resolving Bearer→owner/edit/role, constant-time hash compare, If-Match parsing), `app/routers/` (projections.py, research.py, narrative.py, packet.py, evidence.py, revisions.py, tokens.py, feedback.py, intent.py, actuals.py, places.py, health.py), `app/store/` (base.py Protocol, sqlite.py, postgres.py stub, migrations/), `app/schemas/` (Pydantic request/response incl. the §App-D view-model), `engine/` (compute.py PURE, model.py constants/versions, monthly.py, dag.py overrides, decision.py guardrails+reco, xlsx.py, packet.py, narrative_facts.py), `engine/tests/golden/` (fixtures + LibreOffice recalc via recalc.py). (2) An explicit endpoint→module map for every §25 route: GET/POST /api/projections→projections.py(list owner-scoped/create); GET/PATCH /api/projections/{slug}→projections.py(fetch / update+recompute, If-Match, 409); POST .../duplicate, .../upgrade-model, .../rotate-tokens→projections.py+tokens.py; GET .../revisions + POST .../revisions/{id}/restore→revisions.py; POST .../trash|restore + DELETE→projections.py; GET .../xlsx→packet.py(engine/xlsx.py); GET .../packet→packet.py; GET/PUT/POST .../narrative(:regenerate)→narrative.py; POST .../evidence→evidence.py; POST /api/research→research.py; GET /api/places/autocomplete→places.py; POST /api/feedback→feedback.py (redacted, support_id, NO projection link per §22); POST /api/intent→intent.py(CRM); POST/GET .../actuals→actuals.py. (3) Request/response shapes: every mutation requires Authorization: Bearer + If-Match: <version>; success returns the full §App-D view-model + new version (also as ETag); 409 returns {error, current_version, current_state}; document the compute response = view-model contract field-by-field (reco/metrics/kpis/monthly/rows/overrides/evidence/settings/version) so frontend and backend share one schema. (4) The compute-core contract: signature, determinism guarantee, model_version + compute_schema_version, the override-key format `{node}#{year}`, the non-pinnable-node list, and the monthly→annual roll-up rule. (5) Versioning/upgrade lifecycle (read returns stored snapshot when model_version differs; upgrade-model = new revision). (6) Data-access interface listing exact Store methods and the Postgres-portability rules (string PKs, no SQLite-only SQL, run the suite against both). (7) Ops: reuse timpager railway.toml (volume at /data, DB_PATH=/data/projections.db, healthcheckPath, numReplicas=1, restartPolicy) and litestream.yml shape; document restore drill/RPO/RTO/purge limits. (8) The golden-test gate as a CI-blocking DoD item tied to M1. Cite the engine-reuse reframing prominently as the #1 architectural correction.

## Frontend & Design (React+TS, design system)

**Summary:** The design is unusually well-specified: a working interactive prototype (House of Hope Projection.dc.html) establishes a finance-grade, table-first, dense UI with a decision banner, a 6-tile KPI strip, a Year-1 monthly cash-flow chart+table, a dense 3-year override table, an evidence panel, a sensitivity table, an override-inspector drawer, reason popovers, a two-tab detail page (Projection / Settings & assumptions), a wizard, a list, and a feedback modal. The brand palette is committed (Thriftly green #35644f + warm neutrals) and semantic tokens (success/warning/error/override-tan #cbb7a9) are kept independent of brand, exactly as DESIGN_PROMPT requires. The single most important frontend decision: the prototype computes everything client-side (calcYears/calcMonthly/scenario in support.js), which PRD §13 explicitly forbids ("No client-side computation in v1"). The prototype is a layout + view-model-field-name reference only; production must replace all client math with debounced server compute (<50ms target) plus optimistic preview reconciling to the server-authoritative computed_json. The override cell UX (calculated/editing/overridden states, dashed-underline input cells, accent left-border + dot for overrides, tap popover comparing calc vs override with audit note, per-pin + global reset, downstream-affected hints) is fully designed and maps cleanly to §11/§14. Gaps the prototype defers and the build doc must own: mobile 375 per-year stacked editor, the full error/degraded state set (409 conflict, AI opt-out, research-failed, stale narrative), role share views, Board Packet layout, and real keyboard/AA verification across the table.

**Key decisions:**
- STACK: React 18 + TypeScript + Vite. State: TanStack Query for server cache (the projection computed_json is server-owned), plus a thin local UI store (Zustand or useReducer) for transient UI (editing cell, open drawer, popover position, wizard draft). Do NOT adopt Redux. Charts: hand-rolled SVG as the prototype does (buildChart is ~30 lines and pixel-aligns bars to the monthly table columns) rather than a charting lib, to keep the bar/line dual-scale + break-even marker behavior and bundle size controlled.
- DELETE ALL CLIENT MATH. The prototype's calcYears/calcMonthly/scenario/startupTotal/paybackYears must NOT survive into production (violates PRD §13/§22 changelog item 22). Frontend sends inputs/overrides via PATCH (If-Match: version) and renders the server's computed_json. Optimistic preview is allowed ONLY as a visual 'pending' state that is replaced by the server result on reconcile; never a second math authority. If a cheap client preview is ever wanted, it must be a clearly-labeled estimate that reconciles, and is out of scope for v1.
- ADOPT THE PROTOTYPE VIEW-MODEL CONTRACT VERBATIM (Appendix D) as the compute API response shape so frontend and backend share one vocabulary: reco{tag,headline,sub,color,bg,icon}, m{capital,cashGap,breakeven}, kpis[]{label,value,sub,color}, monthly[]{revenue,expenses,net,cumulativeCash}+breakevenMonth, rows[]{label,group,y1,y2,y3,class:input|computed|overridden|estimated,editable}, overrides[]{node,year,calculated,value,note,pinnedDate,affected[]}, evidence[]{label,value,method,badge,change,meta}, settings{...}. IMPORTANT: server should emit pre-formatted display strings AND raw numeric values (e.g. {raw, display}) so the client never re-derives money/percent formatting and there is one rounding authority (whole dollars / 0.1% per §12.4).
- COLOR/PRESENTATION RECONCILIATION: reco.color/bg currently come from compute in the prototype. Decision: server emits a semantic reco.tag/severity enum (proceed|revise|find_cheaper_rent|raise_cash|delay|do_not_proceed) and the CLIENT maps enum -> token. Do not let the API hardcode hex. This keeps brand-vs-semantic token separation (DESIGN_PROMPT) and lets theming change without an API change.
- DESIGN TOKENS: codify the committed Appendix D palette as CSS custom properties in two layers: brand-* (e.g. --brand-primary #35644f, --brand-deep #1d4733) and semantic-* (--success #257648, --warning #b45309, --error #dc2626, --override #cbb7a9, surfaces --surface-warm #faf9f6/#f6f5f2/#efede9, panel #f3f4f6, lines #cacbc2/#ededed, text #0b1b14/#313335, muted #5b5f61/#989fa4). Cell-state classes (input #f0f9f3 bg + #89cc9f dashed underline, computed white, overridden #f6f5f2 + #5b5f61 left-border+dot, estimated triangle icon) reference semantic tokens only.
- OVERRIDE CELL STATE MACHINE (per cell): calculated -> (click/Enter/Space) editing -> (Enter/blur commit) {if |value-calc|<0.5 -> back to calculated and DELETE the pin; else overridden}; overridden -> (click) popover {Edit override | Reset to calculated}. This matches support.js commit() semantics. The auto-clear-on-equal-to-calc behavior is a deliberate, good UX rule worth keeping. Derived rows + KPIs are non-editable (cursor default, no tabIndex).

## Math Engine & Excel Contract (numerical correctness)

**Summary:** The PRD treats the Python engine as a "reused single math authority" (§13, §23), but a line-by-line read of generate_projection.py shows the existing engine satisfies maybe 30% of what v3.1 requires: it is annual-only, has no monthly cash-flow, no break-even/capital/sensitivity/decision math (§10-§12), no override/DAG resolution (§11/§14), uses the now-removed Year-2 midpoint rule (§7.1 explicitly kills it), and its Excel builder violates the export contract (§18) and edge-case rules (§12.4) today by emitting raw =net/total_rev and =startup/Y1net divisions that produce #DIV/0! when revenue or Y1 net is 0. The engine is effectively a rewrite that preserves the bottom-up driver chain and the blue-input/live-formula styling, not a reuse. Numerical correctness is buildable but only if the build doc pins exact formulas, resolves three open default conflicts, and specifies the override resolution algorithm and the golden-test gate precisely enough to implement. The good news: the existing recalc.py already gives us the LibreOffice formula-error harness, and its error list is the right gate primitive. The hard part is making server-Python, the in-workbook formulas, and LibreOffice recalc agree to <$0.50/0.1pp WITH overrides present, because overrides break the formula graph in ways the current code never contemplates.

**Key decisions:**
- Treat the engine as a versioned rewrite, not a reuse. Keep the bottom-up driver chain (donating_hh = households x share; donations = donating_hh x donate_freq; retail = donations x donation_value; customers = retail / basket; salvage = retail x salvage_pct; total_rev = retail + salvage) and the blue/live-formula Excel styling from generate_projection.py, but build monthly cash-flow, decision metrics, escalator, override DAG, and the new cost lines as new code under a single model_version constant.
- Kill the Year-2 midpoint everywhere. The current engine computes share[2] = (share_y1+share_y3)/2 (generate_projection.py:65) and writes =AVERAGE(B,B) in Excel (line 209). PRD §7.1/Appendix C make Y1/Y2/Y3 all explicit inputs. Excel must emit three blue input cells for share, and the Y2 row must reference its own input cell, not AVERAGE().
- Resolve the labor-% default conflict before build: DEFAULTS=0.60, prototype=40%, Andy=60%, Appendix-B example=0.60, Appendix-D sample=40%. Pick ONE product default (recommend 40% to match the design's headline numbers: capital ~$277,990, Y1 rev ~$426,911, break-even ~month 5 only reconcile at 40%) and make the golden fixtures use it. Slider remains editable.
- Resolve basket-value default: §7.3 says $17, Appendix-D sample says $17.08, example JSON says 17. Pick $17.08 if the golden fixture must reproduce the prototype's ~$426,911 / break-even month 5; otherwise $17. Document the chosen constant.
- Add the new cost lines to the formula spec with exact placement: Marketing & outreach = total_rev x marketing_pct (default 3.75%); Supplies & processing = total_rev x supplies_pct (default 5.0%, REPLACES the old fixed Store/office supplies $3,700 line); annual rent escalator = rent_y1 x (1+escalator)^(y-1) for y in {1,2,3}, escalator default 3.0%. Remaining fixed lines (insurance 2000, internet 3000, pest 300, repairs 1600, security 900, utilities 22300) stay fixed dollars per the engine.
- Specify override resolution as a topological recompute over the DAG in §14: resolve(node) = pin.value if pinned else f(resolve(parents)). No back-solve: pinning a downstream node does NOT mutate upstream inputs; upstream rows that no longer drive any pinned downstream node get a stale flag. Derived/total/margin/KPI nodes are non-pinnable (reject pin writes server-side, not just hidden in UI). Override keys are '{node}#{year}' per §24.
- Make every total/margin/KPI an Excel FORMULA over its components even when components are overridden (§18 'always formulas') so the sheet foots. An overridden component cell becomes a hard-coded orange value with the comment 'Manual override - calc was =<formula> -> $X; set to $Y on <date>'; the total cell stays =SUM(...) / =net/totrev over those cells.
- Centralize all N/A guards in ONE place in the engine and mirror them in Excel: revenue==0 -> margin, sales/sqft, rev-per-donation, rev-per-customer = null; Y1 net<=0 -> payback = null('N/A - no Year 1 profit'); Y1 revenue==0 -> CAGR = null. computed_json carries explicit null + a flags map (§12.4). Excel writes blank cell + comment for every null, and must guard formula denominators with IF(denom=0,"",num/denom) so LibreOffice recalc never yields #DIV/0!.
- Adopt recalc.py's error list as the formula-error gate verbatim: assert total_errors==0 across {#VALUE!,#DIV/0!,#REF!,#NAME?,#NULL!,#NUM!,#N/A}. Run the gate in BOTH states (no overrides, and a fixture WITH at least one component override + at least one N/A path) - the current SKILL.md step 4 only ever recalcs the no-override happy path.

**Must-haves:**
- A frozen formula appendix in the build doc that lists, per node, the exact arithmetic + default constant, sourced from methodology.md and §7.3, including the new escalator/marketing/supplies lines and the monthly ramp. No formula may live only in code.
- model_version constant stamped into computed_json and the .xlsx; recompute on a new engine is opt-in via upgrade-model (§13). Golden fixtures are pinned to a model_version.
- Golden-test gate, CI-blocking, three-way reconciliation: server Python compute == values embedded in computed_json == LibreOffice recalc of the exported .xlsx, within <$0.50 absolute on dollar cells and <0.1pp on percent cells, zero formula errors. Run with overrides AND without. (PRD §13, §18.)
- Cents-internally / display-whole-dollars discipline (§12.4): compute in integer cents or Decimal, round only at display/compare. The tolerance (<$0.50) exists precisely to absorb the rounding delta between Python float/Decimal and LibreOffice double recalc - document which side rounds.
- Override resolution unit tests: pin a component -> total refoots via formula; pin then reset -> returns to computed; attempt to pin a derived/total/KPI -> rejected; pin upstream that no longer drives anything -> stale flag set. Each with an Excel export that recalcs clean.
- Edge-case fixtures that MUST recalc clean and emit explicit nulls: revenue=0 (0% share), Y1 net<=0 (high rent / low share), negative net profit (parentheses + error color, no #NUM!), 0 sq ft blocked at input, outlier share >8% triggers guardrail flag not a math error.
- Year-1-from-monthly-rollup consistency check (§10.1/§10.2): the 12 monthly P&L rows must sum to the annual Year-1 column to the penny; a golden test asserts annual == sum(monthly) so the two surfaces never disagree.
- Excel must have a separate monthly cash-flow tab and the Year-1 P&L column must reference the monthly roll-up cells (§18), not recompute independently - otherwise the two tabs can drift and one will fail the gate.
- A documented decision-metric formula set: break-even revenue solved from fixed+variable structure for net=0 (monthly and annual); startup capital required = sum(startup) + |peak cumulative cash shortfall| + reserve_buffer (default $25k); first-year cash gap = most-negative cumulative cash M0..M12; payback = startup_total / Y1 net with the N/A guard. These are asserted by golden tests, not just rendered.

**Risks:**
- Reuse illusion: §13/§23 call the engine 'reused, single math authority,' which will lead a builder to under-scope. The annual P&L engine is the smaller half; monthly cash-flow + decision metrics + override DAG are net-new and are where correctness bugs will live. If the build doc says 'wire up the existing engine' the estimate is wrong by a large factor.
- Override + formula contract collision: §18 says totals are 'always formulas' AND overridden components are 'hard-coded orange values.' This is consistent (total = SUM over the now-hardcoded cells) but is exactly the case the existing build_xlsx never handles, and it is the case most likely to fail the <$0.50 gate if the server's resolved total is computed differently from the in-sheet SUM. The two must be derived from the same resolved node values.
- #DIV/0! is currently a guaranteed failure: build_xlsx lines 257 (=net/totrev) and 284 (=startup/Y1net) have no zero-guard, so any 0-revenue or 0-Y1-net fixture fails recalc.py's gate immediately. The N/A contract (§12.4/§18) is specified but not implemented; treat as a known defect to fix in the rewrite.
- Float vs Decimal vs LibreOffice double divergence: three engines computing the same chain can differ by sub-cent amounts that compound (e.g., escalator ^ exponent, salvage % chains). Without a single rounding policy the golden gate will flicker. Must standardize on one numeric type server-side and define the comparison rounding.
- Escalator ambiguity: §7.3 says escalator 'applies to Y2-Y3.' Must specify whether it compounds (rent_y1*(1+e)^(y-1)) or is linear, and whether it also escalates NNN opex and the lease-deposit startup line. Different readings produce different Y3 rent and different break-even; pick one and fixture it.
- Two basket-value / labor-% defaults floating in the doc means two different 'correct' answers; whichever a builder picks, the golden fixture and the Appendix-D prototype numbers must be made to agree or QA will chase a phantom mismatch.
- LibreOffice recalc is environment-sensitive (recalc.py depends on office.soffice and a Basic macro install); CI must pin a LibreOffice version or the gate's recalced values can shift across versions, undermining the <$0.50 tolerance.
- Sensitivity (base/downside/upside +-25% on rent & donations, §12.2) multiplies the number of states the gate should cover; if not fixtured, a sign or compounding error in a downside scenario ships silently because the happy path passes.

## Security & Ops

**Summary:** The PRD is unusually security-literate for a v1: §20 already specifies bearer-token capability access with no cookies (CSRF-free mutations), fragment-delivered secrets, token hashing + constant-time compare, CSP/CORS/noindex, rate limits, audit logs, and rotate/revoke; §16/§17 specify retrieval-grounded research and post-generation numeric grounding to defend against LLM injection and hallucinated figures; §22 redacts feedback so no projection link reaches GitHub. The math engine (generate_projection.py) is pure compute with no network, subprocess, secret, or eval surface — safe to reuse in-process or as a sandboxed subprocess; its only IO is json.load(open(argv[1])) and os.makedirs(outdir)+write, so the server must own the output path (never user-controlled) and never pass raw user JSON through the filesystem. The biggest gaps are operational, not architectural: the capability-token model means key loss = data loss with no recovery (§29), there is no spec for the litestream /data-volume restore drill being actually tested, no env-var validation/boot-refuse policy (timpager's strongest pattern, absent here), and the LibreOffice recalc gate (recalc.py) is a heavyweight CI dependency that must be pinned and sandboxed. The timpager reference is a strong ops template but its own litestream.yml points at /app/timpager.db (not the durable /data volume) — do NOT copy that bug; the projections DB must live at DB_PATH=/data/projections.db with Litestream replicating from there.

**Key decisions:**

Required: DB_PATH=/data/projections.db, GOOGLE_PLACES_API_KEY, ANTHROPIC_API_KEY, CENSUS_API_KEY, plus at-least-one AI provider check (Anthropic primary OR OpenAI fallback per §17). - Terms-acceptance gate before export/share, AI-disclosure UI when data is sent to providers, and documented provider data-retention (prefer zero-retention endpoints) + app retention + backup purge limits (§21).

**Risks:**
- Key-loss = data-loss is structural: no login means a lost owner token / lost recovery code permanently orphans a projection with no support path (§29). The one-time recovery code (§20) is the only mitigation and must be surfaced forcefully at create time; document that staff CANNOT recover access (only resolve support IDs), so user expectations match reality.
- Bearer token in localStorage is XSS-exfiltratable; a single stored-XSS (e.g. via unsanitized narrative or evidence fields) yields full projection takeover and, worse, the token also authorizes .xlsx/packet export. Sanitization + enforcing CSP are load-bearing, not nice-to-have.
- LibreOffice in the CI/build path is a heavy, slow, version-sensitive dependency; an unpinned soffice or a headless-mode hang (recalc.py relies on gtimeout/timeout wrappers that may be absent) can flake the release gate or block deploys. Pin the version, ensure timeout is present in the image, and have a fallback assertion path.
- Litestream single-replica + single-volume is a single point of failure; if the restore drill is never exercised, RPO/RTO claims are unverified fiction. timpager's own runbook marks Litestream 'conditional, runs only if LITESTREAM_BUCKET set' — easy to ship with replication silently off. Make LITESTREAM_* required in production (boot-refuse) OR loudly health-check that replication is live.
- Research subsystem fetches arbitrary attacker-influenceable web pages server-side (§16.1) — SSRF risk: a malicious source URL could target Railway's private network (e.g. *.railway.internal, 169.254.169.254 metadata, 10/8). The server fetcher MUST block private/link-local/loopback IP ranges and disallow redirects to them (timpager's net-guard.js private-range list is a good reference for what to block).
- User-attached evidence files (§15/§24 file_ref) introduce file-upload risk (type/size limits, no executable/SVG-with-script storage, served with Content-Disposition + non-executable content-type, ideally off-origin) — the PRD mentions attachments but not upload hardening.
- Abuse without accounts (§29): tokens are free to mint, so research/narrative/feedback endpoints are open to cost-amplification and GitHub-issue spam from anyone who creates a projection. Rate limits + regeneration caps + research caching (§16.6) are the only brakes; under-tuned limits = surprise Anthropic/Places bills.
- Optimistic-concurrency + autosave (§19.3) can race: debounced autosave writing revision snapshots on every settle, combined with multi-tab/shared-edit-link editing, risks lost updates or revision-log bloat if If-Match isn't strictly enforced server-side on every PATCH (the 409 save-conflict state §19.4 must be real, not cosmetic).
- Migrations on deploy (§26) with a single durable volume and no staging DB copy means a bad migration corrupts the live DB; need additive-only ALTER TABLE discipline (timpager's NEVER-DROP-TABLE rule) and a pre-migration Litestream snapshot checkpoint.

**Doc notes:** Produce a SECURITY.md and a DEPLOYMENT_RUNBOOK.md modeled on timpager's, adapted to FastAPI/Python and the capability-token model. SECURITY.md sections: (1) Capability-token model — owner >=256-bit / view_slug >=128-bit / edit + role tokens, CSPRNG generation (secrets module), hashed storage, constant-time compare (hmac.compare_digest), fragment-only delivery, rotate/revoke flow, one-time recovery code; (2) Secret/env inventory with required-in-prod vs optional/graceful-degrade table (DB_PATH, GOOGLE_PLACES_API_KEY, CENSUS_API_KEY, ANTHROPIC_API_KEY required; OPENAI_API_KEY/GITHUB_TOKEN+REPO/CRM_API_KEY/LITESTREAM_* optional) and a boot-refuse policy with no fallback chains; (3) Prompt-injection + grounding rules (untrusted-data framing, unfetched-citation rejection, sanitizeForPrompt-style stripping, post-generation numeric grounding as a test invariant); (4) SSRF hardening of the research fetcher (block private/link-local/metadata ranges, no redirect-to-private); (5) XSS/sanitization (narrative + evidence allowlist sanitization) and enforcing CSP/CORS/noindex header table (enumerate connect-src origins: api.anthropic.com, api.openai.com only); (6) Feedback redaction + support-ID scheme; (7) Rate-limit table per endpoint (per-IP + per-token), If-Match/409 concurrency; (8) AI opt-out guarantee + provider retention/disclosure; (9) file-upload hardening for attached evidence; (10) audit-log contents (mutations, rotations, exports, share-link access). ## Agentic Dev Process (how an AI agent team should BUILD this)

**Summary:** This repo is unusually well-suited to a disciplined agent build loop because the PRD has already done the adversarial brainstorming (Appendix C changelog) and locked a view-model contract (Appendix D) — so the agent team should skip open-ended brainstorming and run plan-first, TDD-enforced, subagent-driven execution per milestone (M0-M7, §28). The single highest-leverage process decision is to treat the compute engine as a verifiable oracle: the Python engine (generate_projection.py) plus recalc.py give us a golden-file + LibreOffice-recalc gate (§13, §18) that is the spine of the whole TDD strategy. The most dangerous gap the process must surface immediately is that the existing engine does NOT meet the PRD: it is annual-only, hard-codes Year-2 = midpoint (generate_projection.py:65), has no monthly cash-flow, no per-year explicit shares, no overrides/DAG, no decision metrics, and uses the OLD cost structure (fixed supplies, 60% labor, no marketing/escalator). So "reuse the engine" really means "fork it into a server-authoritative compute module behind a stable interface, with the old annual script retained only as a calibration golden." Emulate timpager's CLAUDE.md/DEFINITION_OF_DONE/SECURITY/DEPLOYMENT_RUNBOOK conventions (regression registry, mutation-safety quad, boot-refuses-on-missing-secrets, promote-with-healthcheck-verifying-new-build) but ported to FastAPI/pytest. gstack roles map onto the milestone loop as named review gates; Superpowers supplies the inner loop (writing-plans -> subagent-driven-development -> TDD -> verification-before-completion -> code-review).

**Key decisions:**
- Adopt a per-milestone loop (each M0-M7 is a development branch in an isolated git worktree): (1) /office-hours + /autoplan-style plan-mode review on the milestone spec slice, (2) superpowers:writing-plans to produce docs/plans/YYYY-MM-DD-<milestone>.md with bite-sized TDD tasks and a Global Constraints block copied verbatim from the PRD, (3) superpowers:subagent-driven-development to execute task-by-task with a per-task two-stage review (spec compliance + code quality), (4) milestone-end whole-branch /review on the most capable model, (5) /qa browser pass against Appendix D states, (6) /ship -> /land-and-deploy with healthcheck-verifies-new-build. No milestone merges to main without all gates green.
- Make the compute engine the verification oracle and write the golden-test harness FIRST (M1, before feature breadth). Three reconciliation gates per the PRD §13/§18: (a) server compute == stored computed_json, (b) server compute == LibreOffice recalc of exported .xlsx via recalc.py asserting total_errors==0 and abs(cell-delta) < $0.50 / 0.1pp, (c) both hold WITH and WITHOUT cell overrides. Freeze the legacy annual generate_projection.py output (House of Hope config) as a regression golden so the rewrite is provably calibrated against the known-good Longview numbers before adding monthly/overrides.
- Treat the engine rewrite as an explicit, flagged fork, not a 'reuse'. Process rule in CLAUDE.md: the engine is the single math authority, lives behind one module interface (compute(inputs, assumptions, overrides) -> {computed_json, monthly_json, flags}), is version-stamped (model_version) and NEVER silently recomputes stored projections (§13). The PRD-vs-engine deltas (annual-only, Y2-midpoint at line 65, no monthly, old cost structure) become the M1 task list, each delta a TDD task with a failing golden test first.
- Port timpager's CLAUDE.md as the agent constitution, translated to this stack: Top Damage Risks (leak a resolvable projection link into GitHub feedback §22; client-side math §13; cross-owner data access §20; mutation without If-Match/optimistic-concurrency §25; secret in URL path §20), a Mutation Safety quad adapted to capability tokens (auth-by-bearer-token test, owner-scope/isolation test, 409-stale-version test, negative-path test) on every PATCH/POST, and a living Regression Registry seeded from the PRD's known traps (DIV/0 -> N/A null+flags §12.4; override never back-solves upstream §14; derived rows never pinnable §14; narrative figure not in computed_json must be rejected §17; unfetched citation rejected §16).
- Write AGENTS.md (build-process authority, mirrors gstack) and CLAUDE.md (repo rules, mirrors timpager) as TWO files: AGENTS.md = the loop, the review gates, the model-selection policy for subagents, the plan/spec locations; CLAUDE.md = the hard rules, vocabulary, regression registry, doc-index. DEFINITION_OF_DONE.md = the verification bar (below). Keep timpager's 'Docs Are Code' rule: any PR touching the engine, the API contract, or the schema MUST update the matching doc in the same PR.
- Define the verification bar (DEFINITION_OF_DONE.md) in two tiers like timpager. Tier-1 GATE (every commit): pytest green zero failures; on a feature branch not main; no secret in code/logs/responses; every mutation has bearer-auth + owner-scope + If-Match-409 + negative-path tests; engine golden + LibreOffice recalc gates pass. Tier-2 QUALITY (every PR): test-to-code ratio target; threat model for new endpoints; a11y AA check on new UI (keyboard wizard/table/override drawer, no color-only meaning §27); per-provider LLM grounding test (narrative figures validated against computed_json §17; injected web instructions ignored §16); Failure Mode Registry row (provider 429, recalc mismatch, stale 409, save-offline) with Rescued? + Tested? both Y.
- Set the subagent model-selection policy explicitly (Superpowers subagent-driven §Model Selection): cheapest tier for transcription tasks where the plan contains complete code (most M2/M6 CRUD + .xlsx cell wiring); standard tier for the override-DAG, monthly-cashflow, and research-retrieval integration tasks; most-capable for the engine math rewrite (M1) and every milestone-end whole-branch review. Always name the model in the dispatch; never inherit session default. Maintain a .superpowers progress ledger so a compaction never re-dispatches a finished milestone task.
- Gate the whole program behind M-1 pre-build validation (§28) as a process precondition, not a coding milestone: the agent team does NOT start M3+ (research/narrative/overrides) heavy build until the 20-interview / 10-manual-projection / 3-conversion bar is met. Encode this as a literal checklist at the top of AGENTS.md so an eager agent cannot skip it.

**Must-haves:**
- A golden-test harness wired in CI that runs the server engine and recalc.py (LibreOffice headless) on a fixed set of configs (House of Hope + edge cases: revenue=0, Y1 net<=0, 0 sqft blocked, NNN vs gross, with-overrides and without) and FAILS the build on any cell delta >= $0.50/0.1pp, any Excel formula error, or any computed_json mismatch (§13, §18). This is non-negotiable and built in M1 before feature breadth.
- CLAUDE.md + AGENTS.md + DEFINITION_OF_DONE.md present at scaffold time (M0), with a Regression Registry table seeded from the PRD's known traps, before any feature code is written — mirroring how timpager's CLAUDE.md front-loads its 57-row registry.
- Plan-mode review (gstack /autoplan: CEO/eng/design/DX) on each milestone spec slice BEFORE any task code, producing a saved plan in docs/plans/ with a verbatim Global Constraints block — TDD tasks only, no placeholders (superpowers:writing-plans 'No Placeholders').
- TDD enforced as the Iron Law for all engine, decision-metric, override-DAG, and API mutation code: failing test committed and watched-fail first; no production code without a prior red test; bugfixes get a reproducing regression test (systematic-debugging Iron Law). Throwaway research/LLM-prompt spikes are the only allowed exception and must be deleted before the real TDD pass.
- Per-mutation test quad on every PATCH/POST endpoint (§25): bearer-token auth required, owner-scope isolation (never global list, never cross-owner read/write §20), If-Match optimistic-concurrency 409-on-stale, and a negative/abuse path (rate-limit per IP+token §20). No mutation merges without all four.
- Grounding/safety tests as first-class verification, not manual checks: (a) every numeric figure emitted in narrative prose must exist in computed_json or generation is rejected (§17); (b) any citation the LLM returns that was not server-fetched is rejected (§16); (c) web-fetched text injected with instructions is treated as data and ignored. These run in CI with recorded/stubbed provider responses so they are deterministic and cost-free.
- verification-before-completion discipline in every subagent and every milestone close: no 'done/passing/fixed' claim without fresh command output in the same message (pytest output, recalc JSON total_errors:0, a11y check, deploy healthcheck showing the NEW build SHA per timpager DEPLOYMENT_RUNBOOK — a bare HTTP 200 is not enough).
- Feedback-redaction test that asserts no view_slug / edit token / resolvable projection link and no financial field ever appears in a GitHub-issue payload, only the random support_id (§22) — a CI test, because this is the product's top data-leak risk and must be impossible to regress.
- Boot-refuses-on-missing-secret config validation ported from timpager (env-requirements single source of truth): production boot fails if ANTHROPIC_API_KEY / DB_PATH=/data/projections.db / CENSUS / PLACES / GITHUB_TOKEN+REPO etc. are unset; AI keys are at-least-one with documented graceful-degrade so the §21 no-AI opt-out path stays testable.
- A documented Litestream restore drill + RPO/RTO + backup-purge-limit runbook (DEPLOYMENT_RUNBOOK.md) treated as a milestone deliverable (M7), with the volume at /data and DB_PATH=/data/projections.db, and a promote script that verifies the new build SHA before flipping environments.

**Risks:**
- 'Reuse the engine' is a trap: the existing generate_projection.py is annual-only, hard-codes Y2=midpoint (line 65), lacks monthly cash-flow, lacks the three explicit share years, lacks overrides/DAG and decision metrics, and uses the OLD cost structure (fixed supplies, 60% labor, no marketing line, no escalator). If agents treat M1 as 'wire up the existing script' they will build the wrong model. The process must force M1 to be a TDD rewrite against new goldens, with the old script retained only as a calibration reference.
- LibreOffice-in-CI is an environment dependency that will silently break agent verification if not pinned. recalc.py depends on a headless soffice + a user-profile macro; a CI runner without it returns an error dict, not a pass, and a sloppy harness could read that as non-failing. The golden gate must assert status=='success' AND total_errors==0 explicitly and fail closed.
- The monthly cash-flow model (§10), override DAG with topological recompute and no upstream back-solve (§14), and decision-metric solver (break-even/capital-required/sensitivity §12) are the genuinely hard, judgment-heavy tasks. If they are dispatched to cheap subagents on a thin plan they will produce plausible-but-wrong math that the golden tests may not fully cover (goldens check totals, not necessarily ramp shape). Mitigate with most-capable-model dispatch, property-based tests (statement always foots; pinned node uses its value; derived rows never pinnable), and explicit ramp/seasonality test vectors.
- LLM grounding tests are easy to write as no-ops (asserting the happy path) and thereby give false safety. The §16/§17 tests must be adversarial — feed a hallucinated figure and assert rejection, feed an unfetched citation and assert rejection, feed injected 'ignore previous instructions' web text and assert it is stripped — or the trust layer is unverified.
- Capability-token / no-login model means the usual auth test scaffolding (sessions, users) does not apply; agents may copy timpager's session patterns wholesale and introduce a cookie (reintroducing CSRF the PRD §20 explicitly designs out) or leak the edit secret from the URL fragment to the server. The CLAUDE.md must call this out as a hard rule with a pinning test.
- Skipping M-1 pre-build validation (§28). An agent optimized to ship code will treat the validation gate as out-of-scope and barrel into M3-M5. Without an explicit AGENTS.md precondition and a human go/no-go, the team risks building research/narrative/override depth nobody validated demand for.
- Context loss across long autonomous runs: subagent-driven-development warns that controllers without a durable ledger re-dispatch completed work (the most expensive observed failure). With 8 milestones this is a real cost risk; the progress ledger and per-milestone worktrees are mandatory, not optional.
- Over-building via the rich PRD: the document specifies role views, actuals/benchmarks, data-compounding, sensitivity, etc. YAGNI/the milestone fences must be enforced in plan-review so agents don't pull M7 features into M2; the 'smallest shippable loop' (M2: inputs->compute->save->reopen->xlsx) must stay genuinely small.
